# 枪械 LOD

> **适用问题**：其他玩家手持枪械的几何与状态机动画如何按距离降级、简化几何从哪里来、缓存与失败回退的边界；**不包含**：TaCZ 自身的模型/动画/玩法机制，也不重新定义联动业务范围（见[联动决策](../../product-decisions/decisions/mod-integration.md)）。

接入点与可选降级总则见[游戏与扩展接入](README.md)。本页只描述当前机制：KINETIC 用 TaCZ 已经解析好的 display 数据自建一份简化几何，在别人的手上替代 TaCZ 的完整模型；同时可以停掉远处玩家的枪械状态机动画。

## 为什么要自建

TaCZ 自带一套 LOD（`display/guns/<gun>_display.json` 的 `lod` 字段 + `RenderConfig.GUN_LOD_RENDER_DISTANCE`），但它有两个缺口：

| 缺口 | 后果 |
|---|---|
| 第三方枪包普遍不写 `lod` 字段 | `GunItemRendererWrapper.renderByItem` 走 `lodModel == null` 分支，永远渲染完整模型 |
| `GUN_LOD_RENDER_DISTANCE` 默认 0，且 `0` 被解释为"从不使用高模" | 语义与直觉相反，实际效果是默认全量渲染 |

枪械模型的面数远高于玩家模型：TaCZ 默认枪的中位数是 2455 面 / 约 700 方块，ak47 实测 **617 方块 / 2455 面 / 8812 顶点**，是玩家模型（46 方块 / 1104 顶点）的 **8 倍**。一局里十几个玩家都举着枪时，这一项就是主要顶点量来源。

因此 KINETIC 不再依赖 TaCZ 的 `lod` 字段，而是**从完整模型自己减面**。

## 数据来源

TaCZ 的枪包以原版资源包形式注册（`GunPackLoader implements RepositorySource`），display JSON 已经由 TaCZ 解析并常驻，所以 KINETIC 直接读它的解析结果，不重复解析 JSON：

| 需要的东西 | 来源 |
|---|---|
| 完整模型位置 | `ClientAssetsManager.getGunDisplay(gunId).getModelLocation()` |
| 已解析的 Bedrock POJO | `ClientAssetsManager.getBedrockModelPOJO(modelLocation)` |
| 贴图 | `getModelTexture()`，例如 `tacz:gun/uv/ak47` |
| 第三人称缩放 | `getTransform().getScale().getThirdPerson()` |

Bedrock POJO 经 TaCZ 自己的 Gson 再序列化回 JSON，交给 KINETIC 的 Bedrock 解析器。这一趟往返是刻意的：它让整条管线只依赖 KINETIC 自己的 POJO 类型，不把 TaCZ 的类型带进签名。

TaCZ 的 `CubesItem` 注册了 Gson 反序列化器但没有序列化器，逐面 UV 会以 TaCZ 内部字段名 `faceUv` 出来，因此往返时需要改回 `uv`；同时兼容 `geometry.model` 与 `minecraft:geometry` 两种写法。

## 减面

四个阶段，执行顺序固定为 1 → 4 → 3 → 2（编号沿用实现）：先丢掉 TaCZ 从不绘制的标记骨骼，再把实心零件折叠成粗体素盒，然后对保留下来的零件做面级遮挡剔除，最后按自适应阈值决定保留哪些零件。

顺序不能交换：折叠盒要复制"供体方块"的 UV，而面级剔除会把被挡住的面从 UV 表里删掉，先剔除会让复制来的 UV 带空洞、盒子上缺面；自适应阈值又必须用"折叠 + 剔除之后"的每骨骼面数来算预算。

### 阶段 1：丢掉 TaCZ 从不绘制的标记骨骼

这一步是正确性而不是优化。TaCZ 的 `BedrockGunModel` 对 `lefthand_pos` / `righthand_pos` 注册 `LeftHandRender` / `RightHandRender`，对 `muzzle_flash` / `shell` 注册 `MuzzleFlashRender` / `ShellRender`——这些骨骼的方块走的是替换渲染器，**永远不会被画出来**。而 `lefthand_pos` / `righthand_pos` 恰恰是 3×12×4 的手部定位标记方块，最长边 12 远大于任何合理阈值，只按尺寸过滤必然保留。离线渲染复现过这个后果：枪身上多出两块 0.75 格高的板子。规则取 `_pos` 后缀加 `muzzle_flash` / `shell` 两个确切名字；TaCZ 自己也是按名字识别这些骨骼的，所以这个名单和它一样可靠。

可选的 `OtherPlayerGunItemLodSkipAttachments`（默认 `false`）会把 TaCZ 用来挂可安装配件的节点（`mag_standard`、`handguard_default`、`sight`、`muzzle_flash`、`shell` 等，取自 TaCZ 自己的字面量）及其整棵子树一并清空。打开后远处玩家手里只剩枪身，能再省一大块顶点——例如 hk416d 的弹匣 `mag4` 单独就占该模型表面积约 26%——代价是弹匣、瞄具、护木这类标志性部件消失，远处更难分辨武器。注意 `mount`（机匣导轨）不在名单里，它是枪身的一部分。

### 阶段 4：粗体素网格折叠

先算零件（骨骼）的实心度 `fill = Σ 方块体积 / 真实包围盒体积`，只有 `fill ≥ 0.63`（`FILL_THRESHOLD`）才折叠，否则原样保留——弯弹匣、非凸机匣、握把这些包围盒远大于实际体积的零件因此不会被填成方块。真实包围盒用**精确旋转 AABB**（8 个角按 `GeoBuilder` 的约定变换），所以每个折叠盒可证明包含它替代的方块，轮廓只会变大、不会漏掉几何。

折叠过程：把骨骼包围盒切成粗网格（`GRID_LADDER` = (5,3)、(5,2)、(4,2)、(3,2)、(2,1)、(1,1)，从细到粗），每个"有料"格子发出一个盒子——盒子是落在该格子内的方块真实 AABB 的并集，并**裁剪到格子**；空格子不发出任何东西，因此凹截面、弯截面会保留台阶而不是被填平。随后一次 3D 合并把沿同一轴相接、另两轴范围相同的盒子合并。档位取"最细且发出的面数 ≤ 原面数 × 0.70（`COLLAPSE_FACE_TARGET`）"的那一档；最粗一档也省不到就保留原样。

为什么不是整根换一个包围盒：整根换盒会把弹匣的弧度填成方块，简化过头。粗体素网格保留轮廓台阶，只抹平格子内的沟壑，因此省面与轮廓保真可以同时取得。

**工作量上限**：单根骨骼超过 16384 个方块时不折叠。折叠是"网格格子 × 方块"的扫描（最细一档约 45 格、阶梯最多 6 级，即约 270 × 方块数），官方枪最大的一根只有 508 个方块，这个上限只是拦住病态模型在预热线程上跑出秒级停顿；超过上限只是不折叠这根骨骼，其余三个阶段照常。另外每个方块的紧包围盒/体积/面数在每一级只算一次（提到格子循环之外），否则会变成"格子数 × 方块数"次包围盒计算——那正是这个上限原本要防的东西。

### 阶段 3：零件内面级遮挡剔除

只删零件不够：像枪托这种大块实心零件，它内部相邻方块之间的面、以及被别的方块盖住的面，玩家永远看不到，却照样要顶点。Bedrock 的逐面 UV 里"没有条目 = 不生成这个面"，所以把被遮住的面从 UV 表里删掉即可，轮廓一个像素都不会变。

判定只对轴对齐方块生效：旋转方块既不作为遮挡者、也不被遮挡；只有"齐平或超出"的面才算被挡住；轴表显式列出，不做通用几何推断。单骨骼方块数超过 2048 时跳过该骨骼的面级剔除——遮挡判定是 O(n²)，附属包的单骨骼方块数可能远大于官方枪，超过上限只损失一点优化，不会让构建时间失控。

**判定用的是原始 JSON 坐标，而"条目名 → 实际画在哪个半轴"要跟着 `GeoBuilder` 走**，这里出过一个只有几何构造才能发现的错：

| 轴 | 条目 → 实际半轴 | 为什么 |
|---|---|---|
| X | `west` → 最大侧、`east` → 最小侧（**与直觉相反**） | `GeoBuilder` 解析基岩几何时取反 X，并把 west/east 的贴图对调以保持镜像后的贴图正确 |
| Z | `north` → 最小侧、`south` → 最大侧 | Z 不参与取反 |
| Y | `up` → 最大侧、`down` → 最小侧 | Y 不参与取反 |

写反的后果是"删掉外侧可见面、留下内侧看不到的面"——模型上出现破洞，同时白留了看不见的面。镜像布局（`bone.mirror` 或 `cube.mirror`）下 `GeoBuilder` 把 west/east 与 up/down **再**对调一次，所以这四项的正负号整体翻转。

另外两条判定细节：

- **`cube.inflate` 是有符号的**（`GeoBuilder` 直接把它加减到八个角上，负值就是内缩）。取绝对值会把一个内缩的邻居当成外扩的，隔着一条缝也会把别人的面删掉。
- **"有条目"不等于"会画出来"**：`GeoBuilder.addFace` 在 `uv` 或 `uv_size` 缺失/过短时直接跳过。面数与"这块方块有没有面"的判定都按这个口径，否则一个只带 `"west": {}` 的方块会被当成"有面的供体"，折叠出一整根隐形盒子。

### 阶段 2：自适应零件取舍

骨骼体量 `boneMetric = max(最长边, sqrt(表面积)/2)`，阈值取 `max(下限 3.0, min(0.55 × 本模型骨骼体量的 p95, 面数预算))`，其中面数预算把保留零件的折叠后累计面数限制在"去标记后总面数"的 45% 以内。低于阈值的零件**整块**消失，大于等于的**完整**保留；骨骼本身一律保留（只清空 cube 列表），因为 `parent` 名称构成层级，空骨骼不产生几何。

分位与体量**只统计第一个 `minecraft:geometry`**：`GeoBuilder.build` 只取 `get(0)`，其余几何根本不会被渲染。把幽灵几何算进来会让阈值被它的体量抬上去（实测一个 40×40×40 的幽灵骨骼能把阈值从 3.0 抬到 25.7，于是唯一会被渲染的那根骨骼被整根删掉，LOD 直接变成空模型）。

两个体量项缺一不可：只看最长边会删掉由很多小方块拼成的大零件（hk416d 的握把 `group14` 最大方块最长边只有 2.56，会被误删）；只看表面积会删掉又细又长的枪管。相对项随模型自适应，面数预算再把不同枪包的削减幅度拉进同一档，取两者更保守的一个。

为什么必须整体取舍、而不是逐方块过滤：逐方块按尺寸过滤会把一个零件打碎。实测第一版规则在 ak47 上把 21 个主要零件里的 15 个削成了残片（`gastube` 34→1、`group6` 18→1、`bolt` 12→1、`group4` 24→2……），后果是轮廓裂成 3 块（完整模型是 1 块），其中一块是挂在枪身下方的 3635 px 孤立板子，而且没有任何零件看起来是实心的。整体取舍从构造上排除这两类问题。

**实测**（完整模型 → LOD）：

| 模型 | 方块 | 面数 | 保留面数 |
|---|---|---|---|
| ak47 | 617 → 278 | 2455 → 1210 | 49.3% |
| hk416d | 786 → 255 | 3844 → 1320 | 34.3% |
| eos_helenas_nail | 3053 → 1767 | 5765 → 3084 | 53.5% |
| eos_bayonet（附件） | 399 → 235 | 2394 → 1410 | 58.9% |

枪械总体落在约 25–55% 的保留面数区间（本页列出的三把为 34.3%–53.5%）。导轨折成 1–4 个盒子（直的合并回一个），弹匣保留 8–17 级台阶描出弧度，而不是一个砖块。

> ak47 的 1208 是一轮审计前的数字：当时阶段 3 的 X 方向判定是反的（见上表），把 2 个外侧可见面删了、留了 2 个内侧看不见的面。修正方向后变成 1210（+2 = 少删 2 个外面、多删 2 个内面，数量上互相抵消了一部分）。独立的 Python 参考实现 `analysis/gun_lod_compare.py` 有同一个错、也被一起修正，两边现在重新一致——这也说明"用独立脚本量期望值"并不能发现两套实现共有的错。

### UV 与贴图

折叠盒的 UV 取自一个**供体**方块：与该格子相交的最大方块，且只有至少有一个<b>真的会画出来</b>的面的方块才有资格；某个格子的候选全是无面方块（`uv == null`，或逐面条目缺 `uv`/`uv_size`）时该格子不发出盒子（那部分几何在源模型里本来也不绘制）。供体缺的面用**对面**补齐（west↔east、north↔south、up↔down），找不到才退回"第一个真的会画出来的面"。对面优先修掉了主要 artefact：west/east 是 `u=z, v=y`、up/down 是 `u=x, v=z`，用第一个非空面去补 up/down 会把 patch 的两条轴整个配错，长边被压到短边上。

实测 texel 拉伸（模型单位 / 声明 texel）：ak47 p50 1.62 / p90 4.69 / max 36.50，hk416d p50 1.25 / p90 3.42 / max 13.62；`barrel4` 的 36.5 在该骨骼内没有更好的供体，不可再降。使用真实 TaCZ 贴图渲染时，ak47 与 hk416d 的白/未贴图像素都是 **0.000%**（与完整模型相同），且没有 UV 越界。

代价是细部被抹平成色块：导轨槽、螺丝、握把纹路、机匣刻字都会丢失，近看块状、LOD 距离下可接受。验证是软件最近邻采样，没有 mipmap 与各向异性过滤，也没有真实 GPU 验收；eos 枪包贴图不可得，只做了结构性验证；TaCZ 自己的 `lod` 模型没有对比。缺口见[渲染已知问题](../../status/known-issues/rendering.md#背面裁剪与枪械-lod)。

### 几何保证

阶段 2 的取舍以骨骼为单位，从构造上排除"逐方块过滤"造成的悬空碎片与散板；阶段 4 的每个盒子使用精确旋转 AABB 并裁剪到格子，因此可证明包含被它替代的方块，轮廓只会变大、不会漏掉几何。这是结构论证，不是逐像素验收；引入阶段 4 后 LOD 不再是完整模型的顶点子集，旧的"严格子集 / 零独占像素"结论不再适用。

### 尚未处理的保真度缺口

枪械 display 的完整模型同时包含**所有附件变体**（不同枪托、护木、弹匣、瞄具各是一棵子树），TaCZ 按该 `ItemStack` 实际安装的附件逐骨骼设置可见性。KINETIC 在构建 LOD 时拿不到附件状态，因此默认会把所有变体一起画出来；`OtherPlayerGunItemLodSkipAttachments` 只能整片丢掉全部配件节点，不能按当前 `ItemStack` 选择。在 LOD 距离之外这表现为枪托/护木比实际略厚，而不是出现非枪械几何；要完全对齐需要复制 TaCZ 的附件→骨骼映射，目前不做。

## 缓存与提前烘焙

构建分两级缓存：**磁盘**跨进程存活，**常驻内存**跨帧存活。磁盘那一级是"1000 把枪只需要冷烘焙
一次"的落点，常驻那一级只负责最近用到的十几把。

### 磁盘缓存

枪械 LOD 的烘焙产物写进 KINETIC 自己的烘焙缓存根目录，与玩家模型共用同一个 `BakedModelCache`、
同一套 `CACHE_ABI` 与原生 capabilityKey。缓存键必须覆盖**一切会改变烘焙产物**的输入：

| 组成部分 | 为什么必须进键 |
|---|---|
| 枪械 id | 不同枪 = 不同模型 |
| **模型内容哈希** | 枪包更新是**就地改** `geo_models/**` 里的模型文件：枪 id、模型路径、贴图路径与贴图内容全都不变。少了它，更新枪包后 LOD 会继续用旧几何，与 TaCZ 的完整模型对不上（近处新的、远处旧的）。首选直接读模型文件字节（`assets/<ns>/geo_models/<path>.json`，约 0.5 ms）；读不到时退回"序列化已解析 POJO 再哈希"（约 5~15 ms，同样确定） |
| 贴图**内容**哈希 | 枪包换一张同名贴图必须失效，所以用内容而不是路径 |
| 减面参数（体量阈值、是否跳过配件） | 两者都直接改变几何，否则玩家改了配置却拿到旧模型 |
| `GunLodDecimator.RULE_REVISION` | 折叠阈值、网格阶梯、面级剔除算法这些代码常量的改动不体现在任何输入里，只能靠人手递增的版本号 |
| `GunLodFactory.RAW_UV_VERSION` | 它决定 UV 的解释方式；单独升它而没升缓存 ABI 时旧缓存照样通过校验并被复用，LOD 与完整模型的 UV 语义就不一致了 |

命中时只读一个约 200~300 KB 的文件并把 flatbuffer 还原成原生模型——**不解析枪的 Bedrock JSON、
不减面、不解码 PNG**。冷路径（Bedrock JSON 解析 + 减面 + 原生烘焙 + PNG 解码）实测：ak47 约
18 ms、hk416d 约 29 ms、eos helenas_nail 约 51 ms、eos bayonet 约 23 ms，平均约 35 ms；
命中路径是 1~3 ms 量级。

摆放锚点（`thirdperson_hand` 枢轴）存在缓存文件旁边的同名 `.anchor` 附属文件里（三个大端 float）。
不这么做的话，命中时仍然要解析一遍模型才能拿到锚点，磁盘缓存就白做了一半。附属文件缺失、
长度不对或含非有限数一律当作**未命中**并回落到冷路径——宁可多花 35 ms，也不能用错位姿渲染。

**磁盘占用**：每把约 200~300 KB，1000 把约 250 MB。由于减面参数与贴图内容都在键里，改配置或
换枪包版本会生成一整套新文件，而旧文件不会自动清理；淘汰策略尚未实现（共享的烘焙缓存本身也没有
淘汰机制，玩家模型同样如此）。

### 整包复用：枪包没变就一把都不扫

逐把重新读模型与贴图、重新算内容哈希，本身也要成本：1000 把约 150 MB 的读取加哈希，每次启动都要
付一遍。所以预热前面还有一层**枪包级**判断：枪包内容的指纹与上次记录一致时，整包直接跳过——不读
模型、不读贴图、不算哈希。

| 环节 | 做法 |
|---|---|
| 枪包根目录 | `GunLodPackRoots`：扫描 `<gamedir>/tacz/`，命名空间取自枪包自己的 `assets/<ns>/`，**不读 `gunpack.meta.json`**（它可能缺失，也可能与资源目录名不一致） |
| 枪包指纹 | `GunLodPackFingerprint`：压缩包对整个文件做 blake3；目录枪包对全部文件的 `(相对路径, 大小, 修改时间)` 排序后做一次 blake3——只 stat、不读内容，一个 1000 文件 / 33 MB 的枪包约几毫秒 |
| 记录 | `GunLodPackIndex`：`命名空间=指纹` 一行一个包，放在烘焙缓存的 profile 目录下（`CACHE_ABI` 或原生能力变化时跟着换目录），原子写回 |
| 判定 | `GunLodPrewarmPlan`：指纹一致 ⇒ 该命名空间的枪一把都不进队列，直接计为已完成 |

**为什么不能用枪包自己的元数据**：`gunpack.meta.json` 里的 `namespace` / `name` / `dependencies`
在枪包更新后通常原样保留——作者改的是模型和贴图。用元数据当身份，更新过的枪包会被判成"没变"，
新模型永远等不到预热。

**指纹判错的后果是有界的**：它只决定要不要预热，不决定渲染什么。按需路径（`TaczGunLodBuilder.build`）
永远重新算枪 id + 模型内容 + 贴图内容的缓存键，所以指纹误判为"没变"而跳过预热时，画面依然正确，
代价只是那一把枪晚一点才被烘焙（退回改动前的按需异步行为）；误判为"变了"则只是白扫一遍。
两种情况都不会让画面出错。

找不到根目录的命名空间（例如打包在模组 jar 里的官方枪包）拿不到指纹，`isComplete` 恒为 false，
于是回落到逐枪扫描——那类枪包通常只有几十把，代价可以忽略。

### 后台预热

服务器上枪包总量可达约 1000 把，而同屏最多十几把，具体是哪十几把无法预知。`GunLodPrewarm` 把
这份成本挪到玩家还没用到它们的时候：用 `TimelessAPI.getAllClientGunIndex()` 枚举全部枪 id，
逐把走冷路径，但只落盘（`GunLodFactory.bakeOnly`）——**不读回原生模型**，所以预热 1000 把枪的
常驻原生占用是零（否则每把约 200~300 KB，1000 把就是约 250 MB）。

| 状态 | 并发 | 节奏 |
|---|---|---|
| 未进入世界（主菜单 / 加载画面） | `max(2, 核数/2)`，吃满 `ThreadTools` 池 | 每完成一把立刻补下一把，不受 tick 速率限制 |
| 已进入世界 | 1 | 每 20 tick 一把；只要 `GunLodCache` 里有按需构建在等就整帧让路 |

进世界后约单核 5%（单把约 35 ms ÷ 1 秒），1000 把约 17 分钟补完；主菜单那一轮通常已经跑完大半。
`GunLodPrewarm.Policy` 是不依赖 Minecraft 的纯函数，让路与限速两条规则由单测钉住。

**预热不在启动路径上**：它由客户端 tick 驱动、跑在 worker 池上，渲染线程从不等待，所以启动时间
与它无关；启动完成后它继续在后台跑。资源重载时把代次加一，已排进 worker 池的任务在开始执行时
发现代次过期就立刻返回，因此取消是"排空队列"而不是"等它跑完"。资源重载不清磁盘——键里含模型与
贴图的内容哈希，换枪包后旧条目自然不再被命中，枪包索引也按内容指纹记，同样不命中。

**进度显示**：`GunLodPrewarmScreen` 在屏幕角落画一条 120×4 的进度条与一行文字
（`OtherPlayerGunItemLodPrewarmHudPosition`，默认左下角），只在"还有枪等着预热"时出现，
全部热完自动消失；整包复用导致没有活可干时根本不出现。它只是让后台在做什么可见，
显示与否都不影响预热。

只有某个命名空间**全部**枪都成功，才把它的指纹写进索引：只要有一把失败（缺贴图、原生拒绝等），
这个包下次还会重扫，失败的那把才有机会重试。

### 常驻内存

| 层次 | 内容 | 上限 | 失效条件 |
|---|---|---|---|
| `GunLodRegistry` / `GunLodCache` | 按枪械 `ResourceLocation` 的已就绪句柄 | 16 | 客户端资源重载 |
| `GunLodHandle` | 烘焙好的原生模型 + extract 后的 `NativeModelState` + 缓存好的 `RenderType` | 随上一条 | 同上 |
| 磁盘 | 烘焙产物 + 锚点附属文件 | 每把约 200~300 KB | 键变化（换枪包 / 改配置 / 升 `RULE_REVISION`） |
| 磁盘 | 枪包预热索引（`命名空间=指纹`，一个包一行） | 与枪包数同阶 | profile 目录变化（`CACHE_ABI` / 原生能力） |

容量取 16：一局里同屏出现超过 16 种枪械的情况很少，而每个句柄持有一份烘焙原生模型（eos 最大那把 1767 个方块，约 1–2 MB），16 份是可接受的上限。**预热不改变这个上限**——它只写磁盘，不进这张表。淘汰只在渲染线程发生，保证没有正在渲染的句柄被并发释放。

淘汰本身有三条容易写错的细节，都由单测钉住：

- **淘汰最旧的，不是最新的**：`ready` 是插入序的 `LinkedHashMap`，从队首淘汰。淘汰队尾会把"刚构建好、正要被渲染"的那把枪扔掉，而真正冷掉的条目永远留在表里。
- **一次命中可能让缓存超出多条**（连续构建好几把之后才第一次命中），所以要把**每一条**被淘汰的条目都交给释放回调；只释放第一条会让其余的静默漏掉一份原生模型。
- **每次 `get` 都检查容量**，而不是只在命中时检查：只在命中时检查的话，一把"构建好、只画过一帧就再也没人问"的枪（玩家走出视野，或距离判定在取 LOD 之前就返回了 `null`）永远不会触发淘汰，容量上限就变成了软上限。

`dispose()`（淘汰与资源重载用的释放）会同时关掉原生 state **和**烘焙模型：每个句柄持有一份原生烘焙模型，一局里换过几十把枪就会淘汰几十次，重载一次更是把整张表全丢掉。顺序必须是先 state 后模型——`NativeModelState` 里持有烘焙模型的裸指针。只释放 state 的 `release()` 保留给"暂时放掉、之后还要重新 prepare"的场景。

资源重载用 `discard()` 而不是只把引用置空：重载发生时 worker 上通常还有正在构建的枪，它们在重载之后才发布结果；`discard()` 让这些"迟到的构建"当场释放自己，否则每把都漏一份原生模型。

**贴图像素的所有权**：`BakedModelCache` 的供应商契约是"返回借用的像素，由创建者持有所有权"，它自己从不关闭拿到的 `NativeImage`。而 `NativeImage` 没有 Cleaner 也没有 finalizer，只有 `close()` 会释放像素内存——所以"谁 decode 谁 close"。枪械这条路用 `LazyTexture`：命中磁盘缓存时根本不解码（`materialize` 在调用写入方之前就返回），一旦解码就由 try-with-resources 保证关闭。

`GunLodCache` 的线程模型是"渲染线程只读、worker 线程只写"：写方在锁内构造一份**新的不可变快照**并原子替换 volatile 引用，读方只读那个引用。因此渲染线程不加锁，也不会看到 rehash 到一半的 fastutil 容器。

构建失败（缺模型、缺贴图、解析失败、原生拒绝）记为 `unavailable` 且不再重试——避免每帧重复付出失败代价。失败等价于"这把枪没有 LOD"，调用方原样回退到 TaCZ 的完整模型路径。

### 被强杀 / 崩溃时的持久化保证

游戏随时可能被强杀（任务管理器、启动器直接杀进程、掉电），所以本特性写的每一个文件都必须是
"要么不存在、要么完整"：

| 文件 | 写法 | 被强杀后的可见状态 |
|---|---|---|
| 烘焙产物 `<bakeHash>.geo.kinetic-cache` | `AtomicSharedCache`：唯一临时文件 → **校验临时文件本身** → 原子改名（`ATOMIC_MOVE`） | 旧文件或新文件，绝不半截；读取时还会再校验文件里的 bake hash |
| 摆放锚点 `<bakeHash>.geo.kinetic-cache.anchor` | `AtomicFileWrites`：唯一临时文件 → fsync → 原子改名 | 同上；读取时再校验长度与有限性，不合格一律当未命中 |
| 枪包预热索引 `gun-lod-packs.txt` | `AtomicFileWrites` | 旧索引或新索引；行级解析还会丢弃任何残缺行 |

三条推论：

- **不会出现"半截文件被当成有效"**：三个读取端都各自再校验一次内容（bake hash / 长度 + 有限性 /
  行格式），而不是只信文件名。
- **不会出现"还没热却被记成已热"**：索引只在某个枪包**每一把**枪都返回"确实热了"之后才记录；
  而"确实热了"由 `bakeOnly` **写完再读回来确认**（锚点写失败就返回 false，绝不虚报）。任何一把
  没烘好，整包不记，下次重扫——宁可多扫一遍，也不能把"还没热"记成"已经热"。
- **已经记录过的枪包不会因为一次中断而丢失**：索引每次整份重写，旧内容在原子改名成功之前一直完好。

`GunLodPrewarm.Policy.mayRecordPack` 就是上面第二条的可单测形式（`done >= total && failed == 0 &&
fingerprint != null`），由单测钉住"扫了一半 / 有一把失败 / 拿不到指纹 / 空包"四种情形都不记录。

**残留**：`AtomicFileWrites` 保证的是"进程被杀"这一档；掉电与内核崩溃只做到 fsync 文件内容，
不承诺文件系统与硬件层面的持久性。另外，极端情况下（恰好被杀在创建临时文件与改名之间的微秒级
窗口）会在缓存目录留下一个孤儿临时文件；`AtomicFileWrites.sweepStaleTemps` 会按年龄回收，
而且只回收"够老"的，所以两个实例共用同一目录时也不会误删对方正在写的文件。

### 冷启动仍然会发生

预热是尽力而为，而**整包复用把它压缩到只发生在枪包真的变了的时候**：

| 情形 | 启动时要做的事 |
|---|---|
| 枪包没变、上次已预热完 | 只算一遍枪包指纹（约几毫秒/包）就整包跳过，一把枪都不读 |
| 更新过某个枪包 | 只重扫那一个包；其余包照旧跳过 |
| 首次安装、或换了缓存 ABI / 原生能力 | 全部冷启动，后台按两档节奏跑完 |

无论哪种情形，**如果预热还没跑完就进服**，那部分枪仍然是冷的，行为退化到"按需异步构建"——
渲染线程照样不阻塞，只是从该枪进入视野到构建完成之间它以完整模型显示。

## 渲染

`CustomPlayerItemInHandLayer` 在主手与副手的 locator 上渲染简化模型，手部变换与 TaCZ 路径保持一致。

### 比例、大小与摆放

TaCZ 第三人称下施加的完整变换（从 `GunItemRendererWrapper` 字节码读出）是：

```
translate(0.5, 2.0, 0.5)
scale(-1.0, -1.0, 1.0)
applyPositioningTransform(...)   // 沿 positioning -> thirdperson_hand 这条"原点路径"
applyScaleTransform(...)         // translate(0,1.5,0) · scale(v.x,v.y,v.z) · translate(0,-1.5,0)
```

两条关键事实：

- **缩放是逐轴的**（`scale(v.x, v.y, v.z)`），不是等比。KINETIC 只取 `.x` 压成等比会让不等比的枪包变形，所以 `GunLodHandle` 保存三个分量，渲染时逐轴应用。
- **摆放的本质是把 `thirdperson_hand` 骨骼搬到姿态原点**。在两个已知模型里这条路径是 `positioning（枢轴 0,0,0）-> thirdperson_hand`，且**整条路径没有任何旋转**，所以它退化成一次纯平移。

KINETIC 解析 Bedrock 几何时会取反 X（`GeoBuilder` 里 `addPivot(-pivot[0])`、`ox = -(originIn[0]+size[0])/16`），因此 LOD 在 KINETIC 坐标系下施加：

```
translate(anchor.x*sx/16, anchor.y*sy/16, anchor.z*sz/16)   // anchor = (pivot.x, -pivot.y, -pivot.z)
scale(sx, sy, sz)
```

其中 `anchor` 由 `GunLodDecimator.handAnchor` 从模型的 `thirdperson_hand` 枢轴算出，减面不会改变它（骨骼一律保留）。模型与 locator 使用同一套几何、同一个缩放，所以**大小与比例不会因为改用 LOD 而变化**。

`anchor` 与 TaCZ **逐位一致**：TaCZ 的第三人称摆放取 `getPath(modelMap.get("thirdperson_hand"))`，而 `applyPositioningNodeTransform` 在路径为 `null` 时直接返回，所以**模型没有 `thirdperson_hand` 时 TaCZ 不做任何摆放**，模型原点直接落在姿态原点上。实测 eos 枪包 74 把枪里有 48 把没有这个骨骼（且连 `thirdperson` / `fixed` / `ground` / `root` / `positioning` 都没有），因此"回退到别的节点"或"回退到几何中心"都会让这 48 把相对 TaCZ 偏位；KINETIC 只认 `thirdperson_hand`，找不到就返回零平移。

刻意<b>没有</b>照抄 TaCZ 里那两个 `1.5` 常数：它们在方块空间里是整格级偏移，没有客户端无法验证其含义，照抄反而更可能引入错位。KINETIC 的 locator 本身就在手上，所以"把模型的手节点放到 locator 原点"是自洽且可离线验证的选择。若某个枪包的骨骼命名不符合 TaCZ 约定而看起来偏位，用 `OtherPlayerGunItemLodOffsetX/Y/Z` 补偿。

### 其余约束

| 约束 | 做法 |
|---|---|
| 自己的枪不降级 | `entity == mc.player \|\| entity == mc.getCameraEntity()` 时直接返回，不取 LOD |
| 距离判定不分配 | 只用 `Camera.getPosition()` 的 x/y/z 三个 double 做平方比较，不构造 `Vec3` |
| 贴图不额外加载 | 渲染用的是原版 `TextureManager` 按同一 `ResourceLocation` 从资源包加载的 GPU 贴图；烘焙时读到的 `NativeImage` 用完立即关闭 |
| 不重复建对象 | `RenderType.entityCutoutNoCull` / `entityCutout` 每次调用都会新建对象，因此在句柄里缓存一份，背面裁剪开关变化时重建 |

## 两个独立开关

物品 LOD 与动画 LOD 分开配置，语义刻意不同：

| 配置 | 默认 | 含义 |
|---|---|---|
| `OtherPlayerGunItemLodDistance` | 0 | 其他玩家的枪从多少格开始用简化模型；`0` = **一直**用 |
| `OtherPlayerGunAnimLodDistance` | 32 | 超过多少格停掉状态机动画；`0` = **关闭**该优化 |
| `OtherPlayerGunItemLodExtent` | 3.0 | 零件体量的**绝对下限**（单位 1/16 格）；真正阈值还会按模型自适应，调小更保真、调大更省顶点；改完 F3+T 生效。两个减面参数都进缓存键，所以不需要手工清磁盘缓存 |
| `OtherPlayerGunItemLodSkipAttachments` | false | 是否连可安装配件（弹匣、瞄具、护木、枪口装置等）整片不渲染；更省顶点，但丢失辨识轮廓 |
| `OtherPlayerGunItemLodScale` | 1.0 | 在 TaCZ 声明的逐轴缩放之上再乘的倍率 |
| `OtherPlayerGunItemLodOffsetX/Y/Z` | 0 | 位置微调（格），仅在枪包骨骼命名不符约定时才需要 |
| `DisableGunLodPrewarmScreen` | false | 是否隐藏后台预热的角落进度条；它只在还有枪等着预热时出现，隐藏与否都不影响预热 |
| `GunLodPrewarmPosition` | `BOTTOM_LEFT` | 进度条位置 |

动画 LOD 超过距离后不再接管 TaCZ 的换弹、拉栓、开火、攀爬、近战这些状态机动作，但保留持枪/瞄准/跑动等基本姿态：主频道返回 `PlayState.STOP` 而不是 `null`，因为 `hold_mainhand` 控制器在本控制器之后注册并覆盖上半身，主频道停下后持枪姿态仍由 hold 频道给出。

## 失败与降级

| 失败点 | 行为 |
|---|---|
| 未安装 TaCZ | 所有入口返回 `null`，走原路径；TaCZ 类型只出现在 `TacCompatInner` / `TaczGunLodBuilder` 的<b>方法体</b>内，由字节码扫描测试守住 |
| display 缺模型/贴图 | `build` / `prewarm` 返回失败，该枪永久走完整模型 |
| 磁盘缓存缺失、损坏或锚点附属文件丢失 | 当作**未命中**，回落冷路径重建；绝不使用半成品或错位姿 |
| 原生烘焙或 extract 失败 | 句柄 `prepare()` 返回 `false`，本帧回退完整模型；不会每帧重试 |
| 相机未初始化 | 判定失败即不降级（行为与改动前一致） |
| 预热任务抛错 | 只计一次失败并继续下一把，不影响渲染；预热失败不退化成"没有 LOD" |
| 枪包索引读不到、写不进或损坏 | 当作"什么都没预热过"：整包判断全部落空，回落到逐枪扫描。只是慢，不会错 |
| 枪包索引被写了一半（进程被杀） | 原子写保证目标文件不会半截；即使真读到残缺行也只会产生"真实指纹的前缀"，永远匹配不上，该包照样重扫 |
| 锚点写失败 | `bakeOnly` 返回 false，该枪<b>不</b>计入"已热"，于是整包不写进索引，下次重扫 |
| 枪包根目录解析不出、或指纹算不出来 | 该命名空间拿不到指纹，`isComplete` 恒为 false，回落到逐枪扫描 |
| 某个枪包里有枪预热失败 | 该包<b>不</b>写进索引，下次启动重扫这个包，失败的那把才有机会重试 |

`GunLodFactory` 里所有失败路径都收敛到 `null`，不抛出；`TaczGunLodBuilder.build` / `prewarm`
与 `GunLodCache` 同样吞掉一切 `Throwable`。枪包里的畸形模型不会把渲染器带下去。

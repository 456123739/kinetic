# TaCZ 渲染优化实验与验收

本项正在开发，尚未交付。目标为 TaCZ 1.2.0-hotfix 的客户端可选补丁，同时验证启动、内存、稳态帧时间与切枪卡顿。不得以改变武器操作、动画时间、射击或服务端判定换取性能。

## 参考方案

用户提供的[视频](https://www.bilibili.com/video/BV17Ss86mEUB/)与[渲染说明](https://github.com/XColorful/Custom-Gun-Continued/wiki/Rendering-optimization-introduction)描述 Custom Gun Continued 的优化。源码核对固定至 `6d042aeb460d9c378640f026ff5a7ef914d05bcf`，分支 `core1.20.1`。其实现的核心为模型空间几何缓存、动态骨骼子树分块、根矩阵独立绘制及光照字段更新；不是单纯复用临时对象。

参考仓库采用 GPLv3。当前 KINETIC 实验没有复制其实现。后续移植须保留适用的来源和许可证义务。

[上游最终报告](https://github.com/XColorful/Custom-Gun-Continued/blob/6d042aeb460d9c378640f026ff5a7ef914d05bcf/docs/architecture/client/render/benchmark/26.11.35.1-9/测试数据计算报告.md)的环境为 i5-9400F、GTX 1660 SUPER、1080p、Forge 47.4.23、Embeddium、Oculus（未开光影）。每个端点独立启动四次，空手与第一人称 AK47 各测 10 秒。上游报告枪械归因成本从 0.7975 ms 降至 0.2032 ms（减少 74.5%，约 3.92 倍），但持枪总帧耗时为 1.5858 ms 对 0.9830 ms（约 1.61 倍）；1% low 为 334 对 472 FPS。此对比为 TaCZ 1.2.0，不是本项目 1.2.0-hotfix 的测量，也不能证明本补丁已超过参考方案。

[上游换弹报告](https://github.com/XColorful/Custom-Gun-Continued/blob/6d042aeb460d9c378640f026ff5a7ef914d05bcf/docs/architecture/client/render/benchmark/26.11.35.1-5/测试数据计算报告.md)分别覆盖空配件和带配件状态，含 0/3/6 秒触发换弹。它不证明切枪、射击或多人对战场景的收益与正确性。

源码审查发现，全局缓存 128 项/32 MiB 并未计入全部模型自有第一人称分块；CPU 顶点副本与复用构建器也没有全部进入该数值。移植时必须单独核算，不能直接称为整体硬上限。模型空间 VBO 同时涉及法线、雾、光影格式和瞄具绘制顺序，不能只替换一个顶点循环。

## 本机已测实验

以下均为 CPU 微基准，不是游戏 FPS 或整机内存。JDK 17，调用实际 TaCZ 1.2.0-hotfix 的 cube.compile；测试加载器只把原实现中三个 Minecraft SRG 方法名映射为开发名。每立方体 6 面、24 顶点，预热 10 万轮，每个样本 20 万次，7 轮交替测量取中位数。输出消费器保留可见结果，线程分配量由 ThreadMXBean 读取。

| 候选 | 原版 ns/立方体 | 候选 ns/立方体 | 原版/候选分配 B/立方体 | 判断 |
| --- | ---: | ---: | ---: | --- |
| 可复用 Vector3f/Vector4f | 374.49 | 486.57 | 0 / 0 | 淘汰，负优化 |
| 标量位置、复用法线向量 | 374.60 | 389.77 | 0 / 0 | 淘汰，无收益 |
| 标量位置及法线 | 378.48 | 478.78 | 0 / 0 | 淘汰，负优化 |
| 每顶点 `/16` → `*0.0625f` | 268.64 | 282.77 | — | 淘汰，慢 5.3%（JIT 已把除以 2 的幂折成乘法） |

第四项用直接实现 `VertexConsumer`（非反射代理，接近真实 `BufferBuilder`）测得，绝对值 268.64 ns/cube 与前述 277 ns/cube 同量级；`*0.0625f` 与 `/16` 在 200 组随机变换（平移/旋转/非均匀缩放）下 14 个顶点属性逐位相同，但**没有收益**。

单 cube 层面之外，另建了整棵骨骼树的逐帧基线（`TaczModelRenderBenchmarkTest`）：把发布版 TaCZ jar 用构建产物 `intermediateToNamed.srg` 就地重映射后加载（类名相同、只换成员名，POJO 仍留在父加载器供 Gson 使用），夹具为 1 个 root + 19 骨骼 × 3 cube = 57 cube / 1368 顶点，每帧改骨骼旋转并把顶点写进计数消费器。

把立方体全部去掉再测同一棵树，可以把"遍历/矩阵"与"顶点发射"拆开：

| 夹具 | 帧耗时 | 每帧分配 | 折算 |
| --- | ---: | ---: | --- |
| 19 骨骼、0 cube | 3.6 µs | 4,632 B | 遍历+矩阵约占 **18.6%** |
| 19 骨骼、57 cube / 1368 顶点 | 19.4 µs | 5,040 B | 顶点发射 **277 ns/cube**，约占 **81%** |

两个结论：**每帧 4.6 KB 的分配几乎全部来自骨骼变换**（每个节点每次换轴旋转都会新建四元数），
与顶点写入无关（1368 个顶点只多出约 0.4 KB）；**剩下的 81% 是顶点发射**，按 cube 数线性增长。

实测：**19.4 µs/帧，5,040 B/帧分配**（9 轮 × 5,000 帧取中位数，JDK 17）。折算 0.347 µs/cube，与上表单 cube 374 ns 一致，说明该夹具与逐 cube 测法同源。参考方案报告里 "geometry traversal 0.311 ms/帧" 对应的是带配件、含 RenderType 批处理的真实 AK，cube 数约为本夹具的 15 倍，量级一致。

结论：顶点发射按 cube 数线性增长，且与临时对象分配无关；**要动这一项只能把模型空间顶点缓存进 VBO 并按脏子树重建**，单纯改写 CPU 循环没有空间。反过来，剩下的 18.6% 与那 4.6 KB 分配都在骨骼变换里，属于"可以省但不值得为它引入对 TaCZ 内部方法的改写"的量级（约 0.28 MB/s @60fps）。

这表明当前测试条件下 JVM 已通过逃逸分析消除原实现临时向量分配。不能仅按源码里的 new 数量宣称减少 GC 或提高帧率。200 组变换覆盖平移、旋转、非均匀缩放及镜像，两个 cube 实现的 4,800 个顶点各 14 个属性均完全一致；重入回退与消费器异常后的恢复通过。正确性通过仍不足以交付无收益方案。

## 阶段结论

本轮优化已交付并验证（全部在 `test/prone-anim-rework`，833 项测试通过）：

| 方向 | 改动 | 证据 |
| --- | --- | --- |
| 启动 | 命中烘焙缓存不再解析源几何 | 计数回归：热命中 0 次解析 |
| 启动 | 命中缓存只开一次文件（校验与解码合并） | 单遍结构；热加载 157.8 µs/次 |
| 启动 | 派生缓存写入不 fsync | 本机 256 KB 文件 4.3~5.0 → 0.3~1.9 ms |
| 内存 | 默认 352 个动画绑定后释放 proto | `AnimationStoreTest` 逐条断言 |
| 内存 | 删除 LOD 移除后遗留的进程级入口 | 无调用方，行为不变 |
| 网络/CPU | 漫游变量惰性采样 | 3 条行为测试 |
| 性能护栏 | 侧躺状态机无分配断言 | 34.6 ns/call、0.000 B/call |

**未交付**：TaCZ 第一人称几何的模型空间 VBO 缓存。四次 CPU 侧候选全部实测为负优化（+30% / +4% / +28% / +5.3%），全模型基线显示 81% 的帧耗在顶点发射上，剩余收益只能来自 GPU 侧缓存与脏子树重建。

该路径无法在本环境验证：机器只有 llvmpipe 软件渲染（约 2~5 FPS），能看画面是否正确，不能测性能；而模型空间 VBO 牵涉法线逆转置、雾、光影 program 与瞄具绘制顺序，其正确性只有在真实客户端里逐场景对照才能确认。按"不得以未验证的渲染改动换取宣称的性能"的要求，本轮不做落地。

待环境条件具备（可运行带 TaCZ 的客户端），按下列最小面实现：默认关闭的配置项、异常与版本不匹配自动回退原路径、只作用于第一人称枪械、脏子树按节点状态哈希重建、常驻 CPU/GPU 字节数显式上限并在超限时退回即时管线。

## 静态网格化方案（TacZMeshLoader / CGC）的可行性

用户提供的 [TacZMeshLoader](https://github.com/VellEagle/TacZMeshLoader)（约 5000 行，1.20.1 Forge，MIT 未标注）与 CGC 走的是同一条主线的两种实现：**把每帧重算的枪械几何变成一次性烘焙的网格，之后只提交绘制**。差别在缓存粒度：

| | CGC | TacZMeshLoader |
| --- | --- | --- |
| 缓存单位 | 骨骼子树的模型空间网格 | 每个 draw unit 一个 `PolyMesh` |
| 光照 | 烘进顶点后原地改写 uv2，整段重传 | **按光照等级各存一份 VBO，LRU 上限 8** |
| 失效 | 节点状态哈希变化时重建该子树 | 着色器状态变化时整表作废 |
| 绘制 | 每次绘制一个块 | 按 `RenderType` 合批后 flush |

**TacZMeshLoader 的按光照分 VBO 是它的主要内存风险**：一把枪若有 30 个 draw unit，玩家在室内外走动会命中多个光照等级，最坏 30×8 = 240 个 VBO。它自己也知道这点（`LinkedHashMap` 上限 8 + 逐出监听）。CGC 的"原地改写 uv2"只需要一份几何，代价是光照变化时整段重传（约 2.5 MB / 次，它们实测 0.6 ms）。

### 用默认枪包实测出来的规模

TaCZ 1.2.0-hotfix 自带的 `tacz_default_gun` 包里有 **71 把枪**的 bedrock 模型与 71 份动画。逐把统计（解析 `geo_models/gun/*_geo.json`）得到：

- 平均 **677 cube/枪**，AK74M 最多 **1772 cube**，全包合计 **48098 cube**；
- 每 cube 是 1.12 格式的 box = 6 个面 24 顶点 → 平均 **1.6 万顶点/枪**，按 32 B/顶点约 **520 KB**；AK74M 约 1.3 MB；全包约 **37 MB**；
- 每把枪的动画只牵动 **约 17 根骨骼**（71 份动画并集里共 365 个骨骼名，但单把枪远少于此）。

按"只有被动画牵动的骨骼不合并"做静态子树分析，平均会切成 **41 块**（中位数 37，最多 127）——块数远高于直觉，原因是枪的骨骼层级很深，很多静态骨骼的父级带动画，只能自己成块。

### 对本仓库的性价比判断

先摆已知数字（本机实测，见上文与 `TaczModelRenderBenchmarkTest`）：

- 57 cube / 1368 顶点的一把枪：**19.4 µs/帧**；其中顶点发射 81%、遍历与矩阵 18.6%；
- 折算 **277 ns/cube**；TaCZ 默认 AK 约 250 cube 量级 → 约 70~90 µs/帧；
- 参考方案的绘制开销：**每次 draw 约 8~10 µs**（CGC 实测）。

由此可以推出收益的上限与前提：

1. **收益 = 省下的 CPU 发射 − 新增 draw 开销**。若把一把枪切成 30 个块，draw 就要 0.24~0.30 ms，**比原来还慢**；切到 5~8 个块（0.04~0.08 ms）才有净收益。所以"能不能把静态骨骼合并进父块"是成败关键，而不是"有没有 VBO"。
2. **内存**：一份 250 cube 的模型约 250×24 顶点 = 6000 顶点；交错格式按 32 B/顶点算约 192 KB，加索引约 30 KB。若按光照分 8 份就是 1.5 MB/枪。第一人称同屏通常只有 1~2 把枪，但**枪包有几百把**，因此必须：懒烘焙（首次使用时才建）、LRU 上限（例如 8 把）、超限释放。
3. **启动**：绝不能在启动时烘焙整个枪包。按需烘焙 + 后台线程 + 每帧上传预算（例如每帧最多 1 个块、256 KB），首次持枪的那一帧宁可先走原路径，也不能卡一帧。
4. **不破坏动画**：只对"自身局部变换在整段动画里恒定"的节点做静态合并；有动画的节点仍按帧计算矩阵，子块跟随。呼吸/摇晃/后坐力写在根节点上（CGC 的指导意义第一条），根节点变化不触发重建。

### 实测口径下的收益

- **今天的成本（真实模型实测）**：`TaczRealGunBenchmarkTest` 直接跑 TaCZ 1.2.0-hotfix 的渲染路径，夹具是自带枪包里的真实模型：
  AK74M（1772 cube）**243.2 µs/帧**、MK18（1507 cube）**194.8 µs/帧**、db_long（203 cube）**35.2 µs/帧**，
  平均 **136 ns/cube**、单把平均 **157.7 µs/帧**。换算成帧预算：一把 AK74M 约占 16.7 ms 的 **1.5%**。
- **烘焙之后**：CPU 顶点发射降到 0，剩下每帧 41 个块的矩阵与绘制。真实 VBO 绘制约 1~2 µs/块 → **40~80 µs**，约 3 倍改善；若按参考方案 8~10 µs/块计算则是 **330~410 µs，比现在还慢**。这就是必须自己量 draw 成本、而不能照搬结论的原因。
- **内存**：一把 520 KB，懒烘焙 + LRU 上限 8 把 ≈ **4 MB**；不能全包烘焙（37 MB）。
- **启动**：懒烘焙时不增加启动时间；但第一次持枪那一帧要烘 677 个 cube（约 0.7 ms 量级，含分配），必须放到后台线程 + 每帧上传预算，否则就是"换枪卡一下"。
- **FPS 影响要说实话**：单把第一人称枪省 0.1~0.15 ms，相对 16.7 ms 帧预算约 **1%**。真正的场景是**同屏多把枪**（第三人称多名玩家持枪、阴影 pass 翻倍），那里是 0.19 ms × N。

### 原型实测：烘焙后还剩多少 CPU

`TaczStaticBakePrototypeTest` 用同一批真实模型做 A/B。块按根级带 cube 的骨骼划分，是三份模型的实际层级：

| 枪 | 块 | 顶点 | 即时模式 | 只算矩阵（VBO 路线） |
| --- | --- | --- | --- | --- |
| ak74m | 14 | 42,528 | **270.0 µs** | 7.5 µs |
| mk18 | 16 | 36,168 | **214.9 µs** | 2.3 µs |
| db_long | 11 | 4,872 | **36.6 µs** | 1.7 µs |

**顶点回放路线被证伪，必须记录在案。** 同一份烘焙数据如果每帧重新喂给 `VertexConsumer`：

| 枪 | 即时模式 | 回放（空 sink） | 回放（真实写入） | 相对现状 |
| --- | --- | --- | --- | --- |
| ak74m | 270.0 µs | 349.4 µs | 462.2 µs | **0.6×（更慢）** |
| mk18 | 214.9 µs | 289.0 µs | 481.9 µs | **0.4×（更慢）** |
| db_long | 36.6 µs | 40.6 µs | 66.7 µs | **0.5×（更慢）** |

原因很直接：回放仍要对每个顶点发起 `vertex()/uv()/normal()/endVertex()` 四次 Java 调用，42,528 个顶点就是 17 万次调用——省下的只剩"每 cube 的矩阵运算"，那本来就只占一成多。**所以这条优化只有 VBO 一条路：每帧不发顶点，只提交 11~16 次绘制。** 任何"没有 GL 就退回逐顶点回放"的兜底都必须直接放弃，退回即时模式反而更快。

### 结论

方案可行，但**不是"加个 VBO 就变快"**：真正的杠杆是"静态子树合并 + 少量 draw + 光照不改几何"，三者缺一收益会被 draw 开销吃掉。要落地成可验证的东西，最小闭环是：

1. 纯 CPU 的**烘焙器**：把 TaCZ `BedrockModel` 烘成"每块一组模型空间顶点 + 该块的世界矩阵来源"；用与 TaCZ 即时模式**逐位相同**的顶点流做等价断言（可离线做，已有 `TacCubeFixture` 的等价测法可复用）；
2. 静态性分析：统计一把典型枪在整段动画里有多少节点恒定 → 决定块数与收益；这一步不需要 GPU，先把"能切几块"量出来；
3. 再谈 GL：一份 VBO/块，光照变化改写 uv2 区间，异常与光影不兼容时回退原路径。

第 1、2 步不依赖实机，可以先做；第 3 步必须先有"能启动的客户端 + 一把枪"的验证回路，否则又回到"写了但没法证明没坏"。
